Assumptions log: Studease Feature Intelligence System
Each line is an assumption the design depends on. If one stops being true, revisit the decisions that rely on it.

1. Low request volume. Feature requests arrive slowly enough that each submission is processed by the AI as soon as it is saved. At high volume we would batch them and process them on a schedule (e.g. a cron job) instead.
2. Demo-grade build. The system is built to work end to end for the assignment demo, not hardened for real production traffic.
3. Requesters have no accounts. A Requester is identified only by the email address they give when they submit a Feature Request. Upvotes collect no email, so upvoters are never contacted. In a live app, upvoting would require signing in, which would give us their details so they could be emailed too.
4. One Problem per Feature Request. Each Feature Request links to exactly one Problem. A request that bundles several needs is linked to its main need and flagged for the product team instead of being split.
5. Shared production database. The system writes to the existing Studease production Postgres database (Neon), but keeps all its tables in its own schema and never reads or writes the existing Studease tables.
6. Everything is demo data. There are no real users yet, so every row in the feedback schema is synthetic and nothing is marked as seed. `seed remove` empties the whole schema after the Loom and never touches the existing Studease tables. A live version would need to tell seed rows from real ones before deleting anything.
7. Simple GitHub connection. /admin works with one repo (Dustrunner369/studease, formerly study-spot-app, for the demo), set in the config file, using a fine-grained personal access token stored as a server secret. On startup the app asks GitHub for the repo's current name and default branch and keeps them in memory, so a rename only needs a restart; Settings → GitHub only shows the repo and whether the token works. A production version would use a GitHub App and let the team connect a repo in /admin.
8. No real email delivery. Requester updates are shown in an outbox in /admin exactly as they would be sent, but are not actually delivered. A live version would send them through a transactional email service.
9. Jev left out of the first version. Matching uses OpenAI's small model rather than Jev so every decision has a written reason and everything goes through one vendor. At very high volume, Jev would be reconsidered for matching (see ai-costs.txt).
10. Studease product goals written for this project. The three goals used for Strategic fit (help students find new study spots, make students come back, grow the social side) were written for this project; the Studease docs have no official product goals. A real team would replace them with its own.
11. Priority Criteria set once. The criteria are loaded from a config file in the repo and shown read-only in /admin Settings; they are never edited in /admin, so there are no criteria versions and no re-scoring when criteria change. Changing them means editing the file and re-scoring as a build-time step. A live version might let the product team tune them with versioning. (Replaces the earlier "saving the criteria re-scores every open Problem" assumption.)
12. Small Problems. A Decision Brief sends every linked Feature Request to the AI in one call. That fits easily at demo scale; a Problem with hundreds of Feature Requests would need sampling or summarising them in stages.
13. Upvotes limited per browser, not per person. There is no sign-in, so each browser makes a random token once and sends it with every upvote; the server allows one upvote per token per Feature Request, lets that browser take its upvote back, and rate-limits upvotes per IP. Clearing the browser or using another one still gives a new vote, so a determined person can inflate a request's upvotes, and with them the Reach part of the Recommended Priority. A live app would require Studease sign-in to upvote, giving one upvote per person.
14. No sign-in anywhere in the first version. Requesters give an email when they submit, and /admin is protected by an admin key rather than Studease's Firebase sign-in and is_admin flag, so the system still never reads the existing Studease tables (assumption 5).
15. Won't do requests stay on the board. For the demo, a Feature Request whose Problem is marked Won't do stays on the portal and can still be upvoted, so enough interest can bring it back; only Shipped requests are removed. Requesters hear from the team once, when their request ships. A live app might instead tell Requesters about Won't do decisions and progress.
16. Suggest-as-you-type thresholds set on real embeddings. The suggest-as-you-type prototype scored similarity with a word-overlap stand-in, so its show (0.30) and strong-match (0.60) thresholds are placeholders. Both are tuned against real text-embedding-3-small scores on the seed backlog during the build. If real scores spread differently, only the numbers change, not the behaviour.
17. Success measured on seed data, not real use. With no real users, the success metrics measure how well the AI handles the synthetic seed backlog: duplicate catch rate (target 90% or more), grouping accuracy (85% or more) and priority consistency (90% or more of Problems keep the same level across 3 re-scores). The targets were set for this project, not taken from a real baseline; a live version would compare against a real before/after pilot and add time from first request to a set Priority and the share of Requesters who upvote instead of sending a duplicate.
18. The grouping answer key never enters the database. `seed load` reads each seed request's intended Problem from the seed file and, at the end of the load, works out the duplicate catch rate and grouping accuracy and saves them as one row, while every link is still the AI's first answer. The AI never sees the key, and merges, moves or manual fixes in /admin afterwards do not change the numbers. Priority has no answer key, because an intended priority written by an AI would only be one AI judgment checked against another. (Replaces the earlier "answer key lives in the app" assumption.)
19. pgvector lives in the feedback schema. The vector extension (0.8.6) is installed into the system's own `feedback` schema on the production Studease Neon database, not into `public`, so nothing is added next to the Studease tables (assumption 5). Because of this, `seed remove` empties or drops the tables in `feedback` but never drops the schema itself (DROP SCHEMA ... CASCADE would also remove the extension), and the app's migrations must not try to create the extension in `public`.
20. AI failures are rare and handled by hand. With strict output forms and low volume (assumption 1), a failed AI step is uncommon, so the system retries only temporary errors (the OpenAI package's default 2 retries) and otherwise marks the step failed for the product team to retry with one button. There is no background retry queue. Requesters never see an AI failure. At real volume, a queue that retries failed steps on a schedule would replace the manual Retry.
21. AI work after a submit runs in the background inside the app. A submission is saved and confirmed at once, and its embedding, matching and scoring run from an in-memory queue in the same process. If the app restarts mid-step, that request simply stays unmatched and shows under "needs review" (assumption 20). At real volume, a durable job queue would replace it.
